Sub-Agent vs Multi-Agent

SUB-AGENT 一个临时帮手
定位:临时帮手 · 用完即毁
Context:独立 window
调用方式:一般隐式调用
什么时候用:一次性外包（查代码 / 搜资料）· 不想让子任务侵占主任务 context
MULTI-AGENT 一支稳定团队（树状结构 demo）
定位:稳定团队 · Supervisor 调度到 END
Context:各自独立 · 共享的是 STATE
调用方式:一般显式指定
什么时候用:任务大到需要分工、稳定产出的长跑项目

Context Rot：token 数 ↑，推理质量 ↓。每加一个 token，都在跟模型的注意力预算抢额度
Context Rot · 能力衰减是缓降斜坡，不是陡崖(定性示意)

记忆 · 腐烂对策

治腐三策：压缩 / 卸载 / 渐进式披露

三策应对三类症状——对话本身长 → 压缩；单次输出长 → 卸载；工具数量多 → 渐进式披露
①压缩 （Compaction）
症状：对话历史长 → 折叠摘要 + 5 个常驻文件
②卸载 （Tool call offloading）
症状：单次工具输出长 → 保留头尾 + 卸到 FS
③渐进式披露 （Progressive disclosure）
症状：文件/工具/技能多 → 启动挂名字，用到再展开

Part 二 · Harness 的构成
MCP · 组成

MCP = 三个角色

HOST调用模型的一方
Claude Desktop / Cursor / VS Code 等。进程里承载模型会话（远端 API 或本地 LLMs），并管理所有 client。
CLIENThost 内的连接器
每个 client 1:1 接一个 server。在 Host 进程里把模型 FC 输出翻译成 JSON-RPC 双向转发（req/resp）。
SERVER工具方写的小服务
暴露三类能力（Resources / Tools / Prompts）。可被多个 client 同时连（远程模式）。
HOST ↔ MODEL
Function Calling
模型说「我要调 create_issue」 → Host 跑完把结果喂回
+
CLIENT ↔ SERVER
MCP（tools/call · resources/read）
client 把它真的接通、跑完、拿结果
MCP 跟 FC 是不同层——FC 管「开口」，MCP 管「接通」；两者配合用

Part 二 · Harness 的构成
SKILL · 原理

SKILL = 给 Agent 的 「任务 SOP」

通用能力用 MCP，项目任务用 SKILL——复杂度 / 粒度 / 复用范围 都不一样

MCP · 通用能力层

解决「AI 怎么用上外部能力」
通用能力层——一个 server 暴露的工具 / 数据，
所有 AI 客户端都能复用
  • 粒度：按能力拆——一组 Tools / Resources / Prompts
  • 复杂度：高——要写 server 进程、按 MCP 协议通信
  • 复用：跨 AI 应用共享

# PDF 读取技能

## 工作流程
1. 获取用户提供的 PDF 路径。
2. 运行脚本提取文本：python3 …/read.py "<pdf路径>"
3. 如果脚本报错 → 读 tips.txt 中的提示并反馈给用户。
4. 将脚本输出的文本内容返回给用户。
read.py · 实际执行脚本（14 行） 
#!/usr/bin/env python3
import sys
from pypdf import PdfReader

if len(sys.argv) < 2:
    print("用法：python read.py <pdf文件路径>")
    sys.exit(1)

path = sys.argv[1]
reader = PdfReader(path)

for i, page in enumerate(reader.pages):
    print(f"=== 第 {i+1} 页 ===")
    print(page.extract_text())

✓ 金标准 · 贴近专家判断

✗ 贵 · 慢 · 难规模化

成本 × 可复现性 · 三类定位
合分规则——三个打分器如何合成一个试次(trial)的最终判定（严格度 vs 宽容度的权衡）
Weighted · 加权和

Binary · 全部 AND

Part 三 · Agent 的评估
评估 · 非确定性

非确定性度量：单次通过率没有决策价值

同一道题跑 k 个试次（trial）结果不同——用统计指标说话
pass@k = 1 − (1−p)k
k 个试次至少过一个
pass^k = pk
k 个试次全部通过
怎么挑：把"产品对一致性的要求"当成第一性原则——能容忍重试的工具走 pass@k，必须一次就靠谱的代理走 pass^k。
场景 例子 指标 理由
代码生成
一次过为王		 SWE-bench issue 修复 · Claude Code pass@1 关心"首次补丁能否直接合入"，多次"至少一次成"在生产里意义有限。
采样型工具
多方案任选		 brainstorm、代码片段、研究草稿 pass@k
(k>1)		 "出几个方案、有一个能用就行"本身就是合理的产品形态。
To-C agent
每次都得靠谱		 客服代理、电商订单、日程助手 pass^k 每次都期望"没掉链子"——单次 75% 到 pass^3 只剩 42%。
高频长链路
一致性极高		 金融、医疗、Computer use 流水线 pass^k
(k 大)		 多步多次试次串起来——pass^k 反映"端到端不出岔子"。

Harness 不会消失——但它会被重塑

问题不是谁吞掉谁，而是谁在协同谁
部分原本该属 Harness 的能力被吸进模型里，但 Harness 工程 会像 Prompt Engineering 一样——长期作为造好 Agent 的关键技能存在下去

模型决定上限，系统决定下限——但系统的边界一直在变　·　剩下的不变，是把意图翻译成可强制执行的工程约束
